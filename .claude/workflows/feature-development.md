# 新功能开发工作流

## 概述
本工作流定义了 PX4 新功能从需求到发布的完整开发流程。

## 流程图
```
[需求分析] → [架构设计] → [代码实现] → [SITL验证] → [代码审查] → [合并发布]
    PM          PX4/FC        PX4/FC       TEST          PM          PM
               /DRV          /DRV
```

## 详细步骤

### 阶段 1: 需求分析 (Project Manager)
**输入**: 用户需求描述
**输出**: 任务分解文档

1. 分析需求可行性
2. 识别涉及的 PX4 模块
3. 分解为子任务
4. 创建 Issue 跟踪
5. 分配优先级

**交付物**:
- [ ] Issue 创建
- [ ] 任务分解清单
- [ ] 模块映射
- [ ] 优先级排序

### 阶段 2: 架构设计 (对应专家)
**输入**: 任务分解文档
**输出**: 技术方案

1. 分析现有代码架构
2. 设计 uORB 消息接口
3. 设计参数配置
4. 评估影响范围
5. 记录架构决策 (ADR)

**交付物**:
- [ ] 技术方案文档
- [ ] uORB 消息定义
- [ ] 参数设计
- [ ] ADR 记录

### 阶段 3: 代码实现 (对应专家)
**输入**: 技术方案
**输出**: 功能代码

1. 创建特性分支
2. 实现 uORB 消息
3. 实现核心功能
4. 添加参数支持
5. 编写必要注释
6. 自测基本功能

**交付物**:
- [ ] msg/*.msg 消息文件
- [ ] 模块代码
- [ ] 参数定义
- [ ] 自测通过

### 阶段 4: SITL 验证 (Test Expert)
**输入**: 功能代码
**输出**: 测试报告

1. 编写单元测试
2. 配置 SITL 仿真
3. 执行功能测试
4. 分析日志数据
5. 验证性能指标

**交付物**:
- [ ] 单元测试
- [ ] SITL 测试用例
- [ ] 测试通过
- [ ] Flight Review 分析

### 阶段 5: 代码审查 (Project Manager + All)
**输入**: 完整 PR
**输出**: 审查通过

1. 创建 Pull Request
2. 分配审查者
3. 执行代码审查
4. 处理审查反馈
5. CI 测试通过
6. 获得批准

**交付物**:
- [ ] PR 创建
- [ ] 审查通过
- [ ] CI 通过

### 阶段 6: 合并发布 (Project Manager)
**输入**: 审查通过的 PR
**输出**: 代码合并

1. Rebase 合并 PR
2. 更新变更日志
3. 关闭相关 Issue
4. 更新文档
5. 通知相关人员

**交付物**:
- [ ] PR 合并
- [ ] 变更日志更新
- [ ] 文档更新
- [ ] Issue 关闭

## 协作矩阵

| 阶段 | PM | PX4 | FC | DRV | TEST | 说明 |
|-----|:--:|:---:|:--:|:---:|:----:|-----|
| 需求分析 | ★ | ○ | ○ | ○ | - | PM 主导 |
| 架构设计 | ○ | ★ | ★ | ★ | - | 根据模块 |
| 代码实现 | - | ★ | ★ | ★ | ○ | 根据模块 |
| SITL 验证 | - | ○ | ○ | ○ | ★ | TEST 主导 |
| 代码审查 | ★ | ○ | ○ | ○ | ○ | PM 协调 |
| 合并发布 | ★ | - | - | - | - | PM 执行 |

★ = 主要负责, ○ = 辅助参与, - = 不参与

## 质量门禁

1. **需求分析 → 架构设计**
   - Issue 已创建
   - 任务已分解
   - 模块已识别

2. **架构设计 → 代码实现**
   - 技术方案已确认
   - uORB 消息已定义
   - 参数已设计

3. **代码实现 → SITL 验证**
   - 功能已实现
   - 编译通过
   - 自测通过

4. **SITL 验证 → 代码审查**
   - 单元测试通过
   - SITL 测试通过
   - 无阻塞问题

5. **代码审查 → 合并发布**
   - 审查通过
   - CI 通过
   - 冲突已解决

## 回滚机制

如果任何阶段发现严重问题：
1. 记录问题原因
2. 通知相关专家
3. 回退到上一阶段
4. 修复问题后重新推进
