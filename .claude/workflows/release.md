# 版本发布工作流

## 概述
本工作流定义了 PX4 版本发布的标准流程。

## 流程图
```
[发布规划] → [代码冻结] → [测试验证] → [发布准备] → [正式发布] → [发布后]
    PM          PM          TEST          PM          PM          PM
```

## 详细步骤

### 阶段 1: 发布规划 (Project Manager)
**输入**: 发布需求
**输出**: 发布计划

1. 确定发布版本号
2. 确定发布范围
3. 识别必须包含的修复
4. 设定发布时间表
5. 创建发布 Milestone

**版本号规则**:
- `MAJOR.MINOR.PATCH`
- MAJOR: 不兼容的 API/参数变更
- MINOR: 向后兼容的新功能
- PATCH: 向后兼容的 Bug 修复

**交付物**:
- [ ] 发布计划文档
- [ ] Milestone 创建
- [ ] 时间表确定

### 阶段 2: 代码冻结 (Project Manager)
**输入**: 发布计划
**输出**: 发布分支

1. 创建发布分支 `release/x.xx`
2. 停止接受新功能
3. 仅接受关键 Bug 修复
4. 通知所有开发者

**分支策略**:
```
main ──────────────────────────────────►
       \
        └── release/1.15 ──────────────►
                           (仅 bug 修复)
```

**交付物**:
- [ ] 发布分支创建
- [ ] 代码冻结通知
- [ ] Bug 修复流程确定

### 阶段 3: 测试验证 (Test Expert)
**输入**: 发布分支
**输出**: 测试报告

1. 运行完整测试套件
2. SITL 回归测试
3. 关键硬件测试
4. 性能基准测试
5. 生成测试报告

**测试矩阵**:
| 测试类型 | 目标 |
|---------|-----|
| 单元测试 | 100% 通过 |
| SITL 集成测试 | 100% 通过 |
| 硬件测试 | 关键功能验证 |
| 性能测试 | 无明显退化 |

**交付物**:
- [ ] 单元测试报告
- [ ] SITL 测试报告
- [ ] 硬件测试报告
- [ ] 性能基准报告

### 阶段 4: 发布准备 (Project Manager)
**输入**: 测试通过
**输出**: 发布材料

1. 更新版本号
   - `CMakeLists.txt`
   - `firmware.prototype`

2. 准备变更日志
   ```markdown
   ## [1.15.0] - 2024-xx-xx

   ### New Features
   - Feature 1 (#12345)
   - Feature 2 (#12346)

   ### Improvements
   - Improvement 1

   ### Bug Fixes
   - Fix 1 (#12347)

   ### Breaking Changes
   - Change 1
   ```

3. 更新文档
   - 发布说明
   - 参数变更
   - 升级指南

4. 构建发布固件
   - 所有支持的板卡
   - Bootloader (如需要)

**交付物**:
- [ ] 版本号更新
- [ ] 变更日志完成
- [ ] 文档更新
- [ ] 固件构建

### 阶段 5: 正式发布 (Project Manager)
**输入**: 发布材料
**输出**: 发布完成

1. 创建发布 Tag
   ```bash
   git tag -a v1.15.0 -m "Release 1.15.0"
   git push upstream v1.15.0
   ```

2. 创建 GitHub Release
   - 上传固件文件
   - 添加发布说明
   - 标记为正式版本

3. 更新文档网站
   - docs.px4.io
   - 参数参考

4. 发布公告
   - PX4 Discuss
   - Discord
   - 社交媒体

**交付物**:
- [ ] Git Tag 创建
- [ ] GitHub Release 发布
- [ ] 固件上传
- [ ] 文档更新
- [ ] 公告发布

### 阶段 6: 发布后 (Project Manager)
**输入**: 发布完成
**输出**: 发布总结

1. 监控用户反馈
2. 收集问题报告
3. 规划 Patch 发布
4. 发布回顾总结
5. 更新开发路线图

**交付物**:
- [ ] 反馈收集
- [ ] 问题跟踪
- [ ] 发布总结

## 协作矩阵

| 阶段 | PM | TEST | PX4 | FC | DRV |
|-----|:--:|:----:|:---:|:--:|:---:|
| 发布规划 | ★ | ○ | - | - | - |
| 代码冻结 | ★ | - | ○ | ○ | ○ |
| 测试验证 | ○ | ★ | ○ | ○ | ○ |
| 发布准备 | ★ | ○ | - | - | - |
| 正式发布 | ★ | - | - | - | - |
| 发布后 | ★ | ○ | - | - | - |

★ = 主要负责, ○ = 辅助参与, - = 不参与

## 发布检查清单

### 代码冻结前
- [ ] 所有计划功能已合并
- [ ] 关键 Bug 已修复
- [ ] 文档已更新

### 测试验证
- [ ] CI 全部通过
- [ ] SITL 测试通过
- [ ] 硬件测试通过
- [ ] 性能无退化

### 发布前
- [ ] 版本号正确
- [ ] 变更日志完整
- [ ] 固件构建成功
- [ ] 文档同步

### 发布后
- [ ] 固件可下载
- [ ] 文档可访问
- [ ] 公告已发布

## Patch 发布流程

对于 Patch 版本 (x.x.1, x.x.2):

1. 在发布分支上修复 Bug
2. Cherry-pick 必要的修复
3. 运行回归测试
4. 更新 Patch 版本号
5. 创建 Patch Tag
6. 发布 Patch 版本

## 紧急发布流程

对于安全问题或严重 Bug:

1. 立即创建修复
2. 加速测试流程
3. 优先发布 Patch
4. 通知用户升级
